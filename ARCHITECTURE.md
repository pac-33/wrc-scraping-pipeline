# Architecture

**Shape.** Medallion-style zones: ingestion (Scrapy) writes an immutable *landing* zone — raw document bytes in `wrc-landing`, one metadata record per decision in `decisions_landing` (`_id` = the decision identifier). Transformation reads landing only and derives the *curated* zone (`wrc-curated` + `decisions_curated`, files renamed `identifier.ext`), so curated can always be dropped and rebuilt. Dagster models both stages as monthly-partitioned assets with an identity partition dependency; the transformation core is a plain function wrapped by both the Dagster asset and a CLI.

**Partition size: monthly.** The busiest body (WRC) publishes ~150–250 decisions/month, so a month is a few hundred records max across bodies — big enough that per-partition overhead (4 count probes + ~1 search page per 10 records) stays negligible, small enough that a failed partition re-runs in ~1–3 minutes and a backfill progresses visibly month by month. It also matches how the site's search behaves (a stable date filter, inclusive on both ends → partitions are `[1st, last-of-month]`, never overlapping a boundary day) and maps 1:1 to Dagster's `MonthlyPartitionsDefinition`, which gives per-month status, retries and date-range backfills for free. Weekly would multiply request overhead ~4× for no operational gain at this volume; yearly would make failure blast radius and retry cost ~12× worse.

**Rate limiting.** Discovery uses the search page's GET API (found by inspecting its pagination links), so page 1's "of N results" lets the spider fan out all remaining pages in parallel rather than walking next-links. Politeness is adaptive-with-bounds: AutoThrottle (target concurrency 2.0) uses observed latency as a live proxy for server load and never speeds up after a non-200; `DOWNLOAD_DELAY=0.25s` is the floor, `CONCURRENT_REQUESTS_PER_DOMAIN=4` the ceiling; ~2–3 req/s sustained in practice. The scraper sends an honest User-Agent with a contact address, obeys robots.txt (`/en/cases/` is allowed — the disallow is the capitalized legacy path; the one documented, config-gated exception is legacy decision PDFs under `/en/*_Import/`, which allowed case pages link as the canonical documents), and disables cookies. Crucially the budget is per *domain*, not per process: Dagster's `QueuedRunCoordinator (max_concurrent_runs=1)` serializes partition runs so a 24-month backfill is still one polite crawler, not 24.

**Retries.** Scrapy's stock retry ignores `Retry-After` (scrapy/scrapy#3849), so a middleware subclass honors it on 429/503 (delta-seconds or HTTP-date, capped at 120s) and otherwise applies exponential backoff with jitter, 3 attempts, delaying only the affected request slot. Ten *consecutive* retryable failures trip a circuit breaker that closes the spider — a struggling server gets silence; Dagster's `RetryPolicy` re-runs the partition later and idempotency makes the re-run nearly free. Exhausted retries flow to each request's errback, so every missed record is logged with identifier, URL, reason, status and retry count; the run fails only if the reconciliation `found ≤ scraped + failures` breaks (the spec's "200 or 200−X, every X logged" rule, enforced in code).

**Deduplication.** Three layers. (1) *Records*: the decision identifier is Mongo's `_id`; upserts (`$set` + `$setOnInsert`, filtered on `_id`, E11000 retried once) make re-runs converge instead of duplicating, while `first_seen_at`/`first_run_id` provenance survives. (2) *Files*: two hashes per object — `file_hash` (sha256 of stored bytes, integrity) and `content_hash` (sha256 of canonicalized bytes, change detection). The split exists because the server appends a volatile `<!-- Elapsed time -->` comment, verified by double-fetching one page: raw-byte hashing would mark 100% of documents "changed" every run. Unchanged content ⇒ no upload, only seen-markers touched. (3) *Transformation*: curated records carry `source_content_hash`; matching landing content short-circuits re-transformation. Measured end-to-end: second run of 1,000+ documents uploads zero bytes.

**At 50+ sources.** The per-source part of this pipeline is deliberately thin — a spider (URL scheme + selectors), an extraction rule, and source config; everything else (partitioning, hashing, storage layout `landing/body=…/partition=…`, politeness, retry/backoff, reconciliation, logging) is already source-agnostic. Scaling means: a source registry (config-driven spider parameters + per-source rate budgets and robots policy), dynamic Dagster partitions keyed `(source, month)` with per-source concurrency tags instead of one global queue, workers that scale horizontally while rate limits stay per-domain, real S3 instead of MinIO (one env var — the code already speaks generic S3 via boto3), Mongo sharded or swapped per scale needs behind the repository interface, and monitoring promoted from run reports to alerting on the found-vs-scraped reconciliation per source. The landing/curated contract is the piece that must not change: source-specific mess stays in ingestion; curated stays uniform for downstream consumers.
